# Drive folder is chosen with the Google Picker; setup flow teaches the full console

Folder selection uses the Google Picker showing the operator's own Drive folders, not a pasted folder ID or URL. Settings → Drive transcripts → Choose folder opens a `DocsView` over `ViewId.FOLDERS` with folder selection enabled and the folder MIME type set; the picker returns both `id` and `name` so nothing is typed and nothing can disagree with Drive. The button is disabled with "Sign in with Google first" until the Google connection is `connected`, and a failed load of Google's picker script renders an inline error rather than a dead button. A cancelled or failed pick leaves the stored folder untouched. The paste path (`window.prompt` plus folder-ID extraction) is deleted — one way to choose a folder, and it is the one that cannot be typed wrong.

No new credential is needed. The Drive and Picker APIs are enabled in the same Cloud project that already hosts Tasks and Gmail; `setDeveloperKey` is not called because an API key authorises views over publicly available data and this picker is private-data access authorised by the OAuth token, and `setAppId` is not called because it is required for the `drive.file` scope while this app holds `drive.readonly`. The Picker API has no OAuth scope of its own and authorises off the Drive scope already requested.

The picker needs an OAuth access token in the page, which is the one Google call this app cannot make entirely on the server side of the wire. The Google connection mints a short-lived access token from the stored refresh token and hands it to the page for the life of one pick, fetched fresh on every open. There is no second OAuth flow, no second consent, and no second token store: the same OAuth client, the same Cloud project, and the same `drive.readonly` scope the Intake already uses. Because the token necessarily carries all three granted scopes (Workspace APIs offer no down-scoping; Credential Access Boundaries cover GCP resources only), and because an access token is portable while the server is bound to `127.0.0.1` with no authentication (ADR-0001), the token is never persisted, never logged, and is recorded in the README security posture. This is the only place the app loads remote code (`https://apis.google.com/js/api.js`, fetched on click not on page load and remembered for the session), and is a stated exception to ADR-0001's local-first posture.

The Google setup card is the app's setup flow and now teaches the whole console it requires. The API step enables four APIs — Tasks, Gmail, Drive, and Picker — each with its own deep link, and says plainly that the Picker API is the one **Check my setup** cannot verify because the picker runs in the browser and has no server-side surface to probe. The scope step says "all three" and the consent step says "all three permissions" naming the Drive one and what it is for; "both" miscounts are corrected. No step is added, removed, reordered or split — the sequence that works today is the sequence that keeps working. Step order (APIs before scopes) remains correct: Google's Data Access scope table lists only enabled APIs, and a scope granted for a disabled API fails later with the not-enabled error the card already explains.

A partial grant is caught where it happens. When Google returns a token, the app compares what was granted against what was asked for with a pure predicate. If a permission is missing the sign-in is refused with a distinct error naming the missing surfaces in human terms **before** the refresh token is stored, so the previous working connection survives intact. The OAuth callback maps that error to its own Settings redirect reason and Settings tells the operator which permission was not granted and to sign in again leaving all of them ticked, rather than sending them to Data Access to fix a console page that is already correct. A response that echoes no scope list at all is treated as a full grant.

Polling asks the Google connection for state rather than reading a refresh-token string, idles while the state is anything but `connected`, and offers any refused-grant error a poll raises to `observe` so the Shell learns from a poll the same way it learns from a Run. `POST /api/google/check` targets the configured folder when one is set (`drive.files.get` on that folder) and falls back to `drive.files.list` when none is, so a deleted, moved or unshared folder is reported as "Drive folder not found or not accessible" rather than passing.

`Sync now` is retained, deliberately reversing ADR-0012's "no other sync button exists". After choosing a folder, "did that work?" is a question the operator asks immediately, and a two-minute blind wait is where they conclude the app is broken.

## Considered Options

- **Browser-side OAuth for the picker (GIS).** A second OAuth flow with its own token source, a second consent that can disagree with the connection banner, and an `Authorized JavaScript origins` console step that tracks `PORT`. Rejected for contradicting ADR-0008's single token source and for adding console work the server-side mint avoids.
- **Paste-a-folder-ID fallback, including behind a disclosure.** Two code paths and two sets of copy to keep honest, for a failure mode that can be named in one sentence once the picker exists. Rejected; the stored folder identity remains what it always was — the picker writes it, nothing types it.
- **Down-scoped access token for the picker.** Workspace APIs offer no token down-scoping; rejected as unavailable.
- **API key or `setAppId` for the picker.** The key is for public-data views; `setAppId` is for `drive.file` retention. Neither applies to a `drive.readonly` picker over the signed-in user's own Drive; adding either would be a new credential or console field for no authority gained.

## Consequences

The Settings page is the only place the app contacts Google's CDN, and only when the operator clicks **Choose folder**. `GET /api/google/picker-token` is available only when the connection is `connected` and otherwise answers with the existing connection failure hint. Refreshing the stored folder name when the folder is renamed in Drive is out of scope; re-picking updates it. `drive.readonly` and `gmail.compose` are both restricted scopes, so the External + Testing posture and its weekly expiry are unchanged. A grant issued before ADR-0012 (without the Drive scope) is not broken in a new way — **Check my setup** already tells that operator to sign in again — but the next sign-in is now checked rather than assumed.
