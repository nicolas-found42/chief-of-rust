# Modal (modal.com) as an LLM extraction provider — research

_Researched 2026-09-03 against the repo seam plus Modal's official docs (primary sources only; every factual claim below cites the repo file or Modal docs page that owns it). No code was changed. Companion tone/format reference: [public-search-providers.md](public-search-providers.md)._

## Question

Can Modal (modal.com) be added as an LLM extraction provider behind this app's one LLM seam, and if so, what is the cheapest integration shape — (a) reuse the OpenAI-compatible path with a custom base URL + key, (b) a new `ProviderId` with bespoke mapping, or (c) not recommended?

## Answer in one paragraph

**Yes, but it is a bring-your-own-endpoint integration, not a hosted-model integration.** Modal offers no OpenAI/Anthropic-style hosted frontier-model API to call with a single key; every inference URL is a model server the user deploys on Modal's GPUs, either via the one-command managed [Endpoints](https://modal.com/docs/guide/endpoints.md) product (open-weights catalog only) or a self-served vLLM/SGLang [Server](https://modal.com/docs/examples/llm_inference.md). The good news is that both paths speak the OpenAI Chat Completions API and authenticate with an `Authorization: Bearer` header using the same scheme OpenAI uses, so the repo's existing shared OpenAI-compatible completion path fits directly. The recommended minimal path is a **new `modal` `ProviderId` that reuses `openAiCompatibleComplete` with a per-user endpoint base URL** (an Ollama-shaped `modal.baseUrl` config, not a hardcoded URL), starting from an unknown binding declaration so the existing response_format → tool → prompt step-down absorbs whatever the user's deployed recipe supports.

## Key finding, stated explicitly

**Modal has no hosted-LLM / "call our frontier model" inference endpoint.** There is no Modal equivalent of `https://api.openai.com/v1/chat/completions` with a single API key that serves Modal's own models, because Modal trains/hosts no frontier models of its own. What Modal sells for inference is compute behind two user-deployed shapes:

1. **Managed Endpoints** — `modal endpoint create --model Qwen/Qwen3.5-4B` provisions a production LLM endpoint from a catalog of open-weights families (Qwen, Kimi, Gemma4, DeepSeek, Nemotron, GPT-OSS, GLM), plus custom fine-tunes from a Hugging Face repo or Modal Volume ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)). "Browse the full catalog" points at the dashboard Endpoints tab — the catalog is the product surface, not a model-API price list.
2. **Self-served inference servers** — the documented DIY path deploys vLLM (or SGLang) in OpenAI-compatible mode on Modal GPUs behind `@app.server` ([vLLM example](https://modal.com/docs/examples/llm_inference.md), [SGLang example](https://modal.com/docs/examples/sglang_low_latency.md)).

Both serve the OpenAI Chat Completions API at the deployment's own URL, and both bill for GPU/CPU compute with scale-to-zero ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)). Anyone scoping this work as "add a Modal key and call their models" should re-scope it as "let the user paste their Modal endpoint URL plus proxy token."

## 1. The current seam (what adding a provider touches)

The whole app's LLM traffic flows through one seam — `makeCompleteJson(cfg, mockResultPath)` in [`apps/server/src/llm/providers.ts`](../../apps/server/src/llm/providers.ts) — which returns a `CompleteJson` closure over one module's `CompletionRequest { system, user, schema }` (the schema belongs to the calling Module, per the comment at `providers.ts:741`). The touch list for a new provider is fixed and small:

How the existing providers split across the seam's two wiring styles ([`providers.ts`](../../apps/server/src/llm/providers.ts)):

- **Bespoke wiring** — `openaiComplete` posts `response_format: { type: "json_schema", … strict: true }` to the fixed `https://api.openai.com/v1/chat/completions` with `Bearer` auth (`providers.ts:392-417`); `anthropicComplete` forces a `save_extraction` tool with `x-api-key` + `anthropic-version` headers (`providers.ts:419-447`); `geminiComplete` posts `responseSchema` + `responseMimeType: application/json` to a key-in-query URL (`providers.ts:449-472`).
- **Shared OpenAI-compatible wiring** — `openAiCompatibleComplete` (`providers.ts:521-553`) is the one path OpenRouter and Ollama share. It sends the `chatCompletionBody` for a Result Shape Binding and steps down `response_format → forced_tool_call → prompt_only` whenever a 4xx names the refused binding (`refusesBinding`, `providers.ts:556-565`). OpenRouter adds a capability-declaration lookup (`supported_parameters` → `declaredBinding`, `providers.ts:572-639`) so a known model goes straight to its best binding; Ollama skips the lookup and passes `null`, i.e. always starts at `response_format` and steps down on refusal (`providers.ts:663-679`), sending `Bearer` auth only when a key is configured.

The Ollama arm is the template for Modal: configurable base URL + optional bearer key + unknown declaration + step-down.

## 2. Modal API facts (primary sources)

### 2.1 No hosted models; you deploy, then call your own URL

- Managed Endpoints are created per model deployment: `modal endpoint create --model Qwen/Qwen3.5-4B`, with the endpoint ID and dashboard link printed on creation; custom weights ride `--custom-hf-*` / `--custom-volume-*` flags against a catalog base model ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)). Supported families are open weights (Qwen, Kimi, Gemma4, DeepSeek, Nemotron, GPT-OSS, GLM) — there is no proprietary-Modal-model endpoint to select.
- The DIY path is a user-written server (vLLM example serves `MODEL_NAME = "google/gemma-4-26B-A4B-it"` on an H200 via `@app.server`, [vLLM example](https://modal.com/docs/examples/llm_inference.md)); the SGLang variant is positioned the same way ([SGLang example](https://modal.com/docs/examples/sglang_low_latency.md)).
- Consequence for this repo: **the base URL cannot be a constant.** Every user brings a different endpoint URL (`https://<workspace>--<label>.modal.run`-shaped for web functions per the [Web Function URLs guide](https://modal.com/docs/guide/webhook-urls.md); managed-endpoint URLs are shown in the dashboard per the [Endpoints guide](https://modal.com/docs/guide/endpoints.md); shared endpoints route through `https://inference.us-west.modal.direct` per the [Endpoint integrations guide](https://modal.com/docs/guide/endpoint-integrations.md)). Any integration needs a per-workspace endpoint-URL setting, exactly like `ollama.baseUrl` today ([`schemas.ts:62-64`](../../packages/shared/src/schemas.ts)).

### 2.2 The serving shape is OpenAI Chat Completions — yes, OpenAI-compatible

- "Once the endpoint is live, it serves the OpenAI Chat Completions API at the endpoint URL … served under `/v1`, and the model name to pass is the base model repo ID," with `POST <endpoint-url>/v1/chat/completions` taking `{ model, messages }` ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)). The OpenAI Python SDK works by setting `base_url="<endpoint-url>/v1"` ([same page](https://modal.com/docs/guide/endpoints.md)).
- The DIY vLLM server is explicitly "vLLM … in OpenAI-compatible mode," tested with the `openai` client library ([vLLM example](https://modal.com/docs/examples/llm_inference.md)).
- Shared endpoints are likewise OpenAI-routed: "routed on the OpenAI `model` field, so the model ID is the endpoint's hostname, for example `my-endpoint.us-west.modal.direct`," with `GET /v1/models` listing reachable endpoints ([Endpoint integrations guide](https://modal.com/docs/guide/endpoint-integrations.md)).

### 2.3 Auth: proxy-token pair as Bearer (OpenAI scheme) or split headers

- Endpoints/Servers require authentication by default; Web Functions are public by default and opt into it with `requires_proxy_auth=True` ([Proxy Tokens guide](https://modal.com/docs/guide/webhook-proxy-auth.md)).
- A proxy token is a Token ID (`wk-…`) / Token Secret (`ws-…`) pair created in dashboard settings or via `modal workspace proxy-tokens create`; the secret shows once ([Endpoints guide](https://modal.com/docs/guide/endpoints.md), [Proxy Tokens guide](https://modal.com/docs/guide/webhook-proxy-auth.md)).
- Requests authenticate either as separate `Modal-Key` / `Modal-Secret` headers or joined with a period as a single `Authorization: Bearer wk-<id>.ws-<secret>` header — and the docs call out explicitly that "[t]his is the same scheme the OpenAI API uses (`Authorization: Bearer <api-key>`), so the combined value can be used as the API key in any OpenAI-compatible client or gateway" ([Endpoints guide](https://modal.com/docs/guide/endpoints.md), [Proxy Tokens guide](https://modal.com/docs/guide/webhook-proxy-auth.md)).
- Consequence for this repo: the existing `apiKey` config field carries the combined `wk-….ws-…` value verbatim, and the seam sends it as `authorization: Bearer ${cfg.apiKey}` — byte-for-byte what the Ollama arm already does when a key is present (`providers.ts:669-672`) and what OpenRouter does unconditionally (`providers.ts:647-655`). No new header plumbing is needed. (Modal *account* API credentials — `MODAL_TOKEN_ID`/`MODAL_TOKEN_SECRET` used by `modal curl` for transparent auth — are a separate, higher-latency testing path per the [Endpoints guide](https://modal.com/docs/guide/endpoints.md), not the app's runtime auth.)
- Note the failure mode this avoids: because the combined token rides the standard `Authorization` header, the split-header form is only needed "when you need to leave the `Authorization` header free for another token" ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)) — not this app's case.

### 2.4 Model story: which `model` string to send

- Managed endpoints: "the model name to pass is the base model repo ID (for catalog and Volume models) or your custom Hugging Face repo ID" ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)). So `DEFAULT_MODELS.modal` cannot be one global constant in the useful sense — the sane default is empty (like `mock: ""` in [`schemas.ts:19-26`](../../packages/shared/src/schemas.ts)) with Settings prompting the user to paste the repo ID shown in their endpoint dashboard, or a catalog example such as `Qwen/Qwen3.5-4B`.
- Shared endpoints differ: the `model` field carries the endpoint hostname (`my-endpoint.us-west.modal.direct`) ([Endpoint integrations guide](https://modal.com/docs/guide/endpoint-integrations.md)). The model field is already free text in Settings, so both fit, but the Settings help text should say which form the configured base URL expects.
- Secrets (unrelated to inference auth, but the likely confusion): Modal *Secrets* inject credentials into the user's *deployed functions* as environment variables via dashboard/CLI/SDK ([Secrets guide](https://modal.com/docs/guide/secrets.md)) — that is the user's Modal-side setup, not anything this app calls.

### 2.5 Operational behavior that constrains the seam

- **Scale-to-zero cold starts.** Endpoints "scale up under load and down to zero when idle" ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)); the DIY server example uses `scaledown_window=15 * MINUTES` ([vLLM example](https://modal.com/docs/examples/llm_inference.md)). A cold endpoint adds wake latency to the first call of a run. The seam's per-call ceiling (`MODEL_REQUEST_TIMEOUT_MS = 300_000` in [`packages/shared/src/llm.ts`](../../packages/shared/src/llm.ts), asserted >186 s in `providers.test.ts:76-78`) already tolerates slow first tokens, so no timeout change is indicated — but e2e tests against a real Modal endpoint should expect first-call latency, not mock latency.
- **No capability declaration endpoint.** Unlike OpenRouter (which exposes per-model `supported_parameters` for `declaredBinding`, `providers.ts:578-639`), Modal documents no equivalent discovery surface — only the shared-endpoint `GET /v1/models` listing, which lists reachability, not binding support ([Endpoint integrations guide](https://modal.com/docs/guide/endpoint-integrations.md)). So a Modal arm must behave like Ollama (declaration `null`, step down on refusal), never like OpenRouter (declared binding up front).
- **Structured-output support is recipe-dependent and undocumented at the Modal layer.** The Modal docs promise OpenAI *chat* compatibility, not `response_format: json_schema` or `tool_choice` support specifically; those depend on the serving engine (vLLM supports both upstream, and the DIY example even enables `--enable-auto-tool-choice` with tool-call parsers — [vLLM example](https://modal.com/docs/examples/llm_inference.md)) and the deployed recipe. The step-down loop is therefore load-bearing for Modal, not a nicety: strict schemas may 400 on some deployments and succeed on others. This must be verified live per endpoint (see Open questions).

## 3. Integration options

### Option A — Reuse the OpenAI-compatible path with a custom base URL + key (cheapest, and recommended in its `modal`-id form)

Concretely: add `modal` to `PROVIDERS` with a `modal: { baseUrl }` config section, and implement `modalComplete` as a thin wrapper over `openAiCompatibleComplete` with the URL `<baseUrl>/v1/chat/completions`, `Bearer` auth from the combined proxy token, and declaration `null` — i.e. the Ollama arm with mandatory auth. All of §1's touch list still applies (vocabulary, dispatch, normalization, 5 shell call sites, Settings, migration taxonomy, tests), but **no new wire code, no new header scheme, no new response readers**: `readChatResultShape` already handles both `response_format` and `forced_tool_call` answers (`providers.ts:297-305`).

Why a new id rather than literally reusing the `ollama` provider entry: the `ollama` id carries the wrong default URL, the wrong Settings label ("Ollama (local model)"), key-optional semantics, and — worst — failure diagnostics that would blame `ollama` for a Modal outage (`ModelCall.provider` flows into every classification in `providers.test.ts:468+`). A distinct `modal` id reuses 100% of the wire path while keeping defaults, help text, and diagnostics honest. The marginal cost over id-reuse is one enum member plus one ~10-line function.

An even cheaper interim exists with zero code changes: point the existing Ollama `baseUrl` at the Modal endpoint URL and paste the `wk-….ws-…` pair as the Ollama key — `ollamaComplete` already appends `/v1/chat/completions` and sends `Bearer` when a key is set (`providers.ts:663-679`). That works as a local spike, but it should stay a spike: it mislabels diagnostics and steals Ollama's single base-URL slot.

### Option B — New `ProviderId` with bespoke request/response mapping (not needed)

Nothing about Modal's wire shape justifies bespoke code today: the documented request is `{ model, messages }` POSTed to `/v1/chat/completions` with Bearer auth ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)) — exactly `chatCompletionBody`'s `response_format` binding — and the documented auth header is exactly the seam's existing one. Bespoke mapping would only be indicated if live probing shows Modal's recipes rejecting the seam's strict `json_schema` envelope in a way the step-down cannot absorb (e.g. hanging instead of 400ing, or 200-carrying an error the seam misclassifies) — in which case the fix belongs in the shared `openAiCompatibleComplete` refusal handling, not in a Modal-only fork. Do not pre-build this.

### Option C — Not recommended (rejected)

Rejection would only be justified if Modal lacked OpenAI compatibility or required SDK-side signing — neither is true per the docs cited in §2. The genuine cost is product, not protocol: each user must deploy (or be given) an endpoint and paste two values (URL + proxy token) instead of one key, and structured-output support varies by deployment. That argues for careful Settings help text and live verification, not for declining the provider.

## 4. Recommended minimal path

1. `packages/shared/src/schemas.ts`: append `"modal"` to `PROVIDERS`; add `modal: ""` (or a catalog example) to `DEFAULT_MODELS` — note §2.4's caveat that no single default model is meaningful; add `modal: z.strictObject({ baseUrl: z.string().default("") })` beside `ollama`; extend `ConfigUpdateSchema` to accept `modal.baseUrl`.
2. `apps/server/src/llm/providers.ts`: add `baseUrl`-style endpoint field to `LlmConfig` (ideally rename-neutral, e.g. reuse the `baseUrl` name the shell already threads); add `modalComplete` mirroring `ollamaComplete` but with mandatory Bearer auth; add the `case "modal":` arm in `makeCompleteJson`; extend `initialCall` only if a modal-specific default binding is ever declared (today it should stay `response_format` like every non-Anthropic provider, `providers.ts:700-702`).
3. `apps/server/src/config.ts` + `apps/server/src/migration/workspace.ts`: default the section; classify `"modal.baseUrl"` as `non-auth-workflow-configuration` (it is a URL, not a secret — the proxy token stays in `apiKey`).
4. `apps/server/src/composition/shell.ts` (5 sites): pass the modal endpoint URL through alongside `apiKey`.
5. `apps/web/src/pages/SettingsPage.tsx`: `PROVIDER_OPTIONS` + `PROVIDER_SHORT` entries; `PROVIDER_KEY_URLS.modal` pointing at the proxy-token docs (`https://modal.com/docs/guide/webhook-proxy-auth`); an endpoint-URL field shown for `modal` exactly where the Ollama base-URL field shows for `ollama`; help text naming both values (endpoint URL from the endpoint dashboard, `wk-….ws-…` combined token as the API key, model = base repo ID or shared-endpoint hostname per §2.4).
6. Tests: `tests/src/unit/providers.test.ts` — modal happy path (URL `${base}/v1/chat/completions`, `Bearer wk-….ws-…`, `response_format: json_schema`) plus a step-down case (400 naming `response_format` → forced tool call), mirroring the `ollama:` cases; `tests/src/unit/config-store.test.ts` — modal defaults/normalization. No new test harness: the existing fetch-stub + declaration-stub setup already covers this shape.

## 5. Open questions (need a live endpoint, not more docs)

1. **Strict-schema acceptance per recipe.** Does the managed-Endpoints recipe accept `response_format: { type: "json_schema", json_schema: { strict: true } }` and forced `tool_choice`, or does it 400 to the step-down (fine) vs. misbehave (needs seam work)? The docs promise chat compatibility only; verify with one strict call and one forced-tool call against a real endpoint.
2. **Cold-start latency distribution.** How slow is the first call after scale-to-zero on a catalog endpoint, and does it fit inside the existing 300 s ceiling with margin for a multi-stage run? One wake-then-call timing pass answers it.
3. **Shared vs. dedicated URL default.** Should Settings default the base URL to `https://inference.us-west.modal.direct` (shared-endpoint routing, hostname-as-model per the [Endpoint integrations guide](https://modal.com/docs/guide/endpoint-integrations.md)) or leave it blank for a dedicated endpoint URL? Depends on whether shared endpoints are generally available or gated — unresolved from docs.
4. **401 taxonomy.** What status/body does a bad/rotated proxy token produce (the [Proxy Tokens guide](https://modal.com/docs/guide/webhook-proxy-auth.md) shows a 401 with a `modal-http:` body prefix for web functions)? Confirm the seam classifies it as `http_error` with an actionable message rather than something cryptic.
5. **Regional routing.** The `--routing-region` / `--compute-region` placement controls ([Endpoints guide](https://modal.com/docs/guide/endpoints.md)) affect latency but not the wire shape — document the user's region choice in Settings help text only if Q2 shows it matters.
